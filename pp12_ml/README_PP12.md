# PP12 ML: классификация строительных задач и улучшение генерации описаний

## Цель

PP12 сохраняет тему существующей функции приложения - генерации описания задачи по названию через локальный LM Studio API - и добавляет отдельную обучаемую ML-часть.

Новая ML-часть должна определять категорию строительной задачи по короткому названию и использовать эту категорию для улучшения prompt к LLM. Это позволяет:

- уточнять тип работ в prompt;
- подбирать похожие эталонные примеры из датасета;
- стабилизировать стиль делового описания для карточки задачи;
- не вмешиваться в существующий WPF-код до отдельного этапа интеграции.

## Архитектура

Решение разделено на два независимых слоя:

1. Существующая LLM-часть в WPF-приложении.
   В проекте уже есть вызов LM Studio для генерации описания задачи. Он остается без изменений на Phase 1.

2. Новая ML-часть в `pp12_ml`.
   Здесь размещаются датасет, notebook обучения, FastAPI-сервис, prompt builder и клиент LM Studio для будущей интеграции.

Поток обработки в новой реализации:

1. Пользователь или WPF-приложение передает `title`.
2. ML-сервис нормализует название задачи.
3. Классификатор TF-IDF + линейная модель предсказывает категорию.
4. Сервис ищет похожие примеры в датасете в той же категории.
5. Prompt builder собирает улучшенный prompt для LM Studio с учетом:
   - названия задачи;
   - предсказанной категории;
   - названия объекта, если оно передано;
   - трех похожих примеров;
   - требования делового и краткого ответа.
6. При настроенном endpoint LM Studio сервис отправляет prompt и возвращает структурированный JSON.

## Используемые подходы

- Готовая LLM: локальная модель через LM Studio API.
- Дополнительная маленькая ML-модель: классификатор названий задач по 6 категориям.
- Признаки: TF-IDF по полю `title`.
- Модели в notebook: `LogisticRegression` и `LinearSVC`.
- Артефакты после обучения:
  - `pp12_ml/artifacts/best_model.joblib`
  - `pp12_ml/artifacts/tfidf_vectorizer.joblib`
  - `pp12_ml/artifacts/label_encoder.joblib`

## Важное ограничение Phase 1

Phase 1 не меняет существующее WPF-приложение. Все новые файлы лежат внутри `pp12_ml`. Интеграция с `praktik` должна выполняться отдельным этапом после обучения модели, проверки API и подготовки контрольных примеров.

## Быстрый запуск

Notebook:

```powershell
cd C:\Users\User\source\repos\praktik
py -m venv pp12_ml\.venv
pp12_ml\.venv\Scripts\python.exe -m pip install -r pp12_ml\requirements-dev.txt
pp12_ml\.venv\Scripts\python.exe pp12_ml\scripts\run_notebook.py --save-executed
```

Сервис:

```powershell
cd C:\Users\User\source\repos\praktik\pp12_ml\service
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Если артефакты модели еще не созданы notebook-ом, сервис вернет понятную ошибку для `/predict-category` и `/generate-description`.

## Допущения

- Реальные обучающие данные из текущей БД на Phase 1 не извлекались, чтобы не менять приложение и не зависеть от локального SQL Server.
- Датасет заполнен правдоподобными `simulated`-примерами в едином деловом стиле.
- Текущий C#-код с LM Studio используется как ориентир по смыслу prompt и точкам интеграции, без рефакторинга.
